# 客户与指定角色数据范围

本设计细化 Task 6 已要求的客户示例和指定角色范围，延续新 API 与 MongoDB 模型，不引入旧系统数据适配。

## 范围规则

- 角色 `dataScope` 为 all/self/roles；`dataScopeRoleIds` 为最多 32 个活动角色引用。仅 roles 模式接受非空选择，其他模式必须为空。PATCH 按合并后的字段校验，修改模式时调用方显式同步选择。
- 有效范围是各角色范围的并集：all 优先，其次 roles 的角色 ID 并集，自身始终包含在内。每次认证从数据库读取最新角色权限与范围，不信任 JWT 中的角色信息。
- 指定角色范围表示可访问这些角色成员拥有的数据，不是继承这些角色的操作权限。
- 角色授权必须同时满足操作权限子集和范围子集；self 操作者不能授予 roles/all，roles 操作者只能授予自身已覆盖角色的子集。角色分配使用同一检查，不能通过分配已存在的大范围角色绕过。
- 非 all 操作者不能给范围内成员附加范围外的自身型角色；成员资格会影响其他管理者的数据可见性。允许分配自身已有角色、可管理的成员角色，或数据范围受限于自身范围的 roles 型委派角色。`/roles/assignable` 仅需 roles.assign，返回有界且可搜索的最小角色选择项，不泄露全局权限目录。
- 被其他活动角色作为范围引用的角色不能删除；角色分配和范围引用校验使用已有 RBAC 事务锁，避免并发悬空引用。
- 用户列表和用户操作也执行自身/指定角色过滤；指定角色用户的创建与角色调整后仍须处于操作者范围，且所有授予权限和范围都不能扩大。
- MongoDB RBAC schema 从本项目 v1 显式迁移到 v2，填充新字段并验证版本；运行时只消费新形状，不提供旧 DTO/字段别名。此迁移属于新产品自身演进。

## 客户资源

- `/api/v1/customers` GET/POST；`/{id}` GET/PATCH/DELETE。权限 `customers.read/write`，版本更新和软删除与审计同一事务。
- 字段：code（活动唯一，忽略大小写）、name、contactName、phone、email、note、status(active/archived)、ownerId。归属默认当前用户，明确转移时必须是活动用户且在操作者范围内。
- all 访问全部客户；self 只访问自身客户；roles 访问自身及所选角色成员的客户。查询在服务端关联当前用户角色过滤，不把全量客户下载后筛选，也不缓存可能过时的成员 ID 清单。
- 范围外记录的读取、修改和删除返回 404；向范围外归属人创建/转移返回 403。禁用用户仍可由有范围权限的管理员维护其既有客户；新归属必须启用。
- 有未删除客户的用户不能删除，需先转移归属；客户创建、转移与用户删除共用 RBAC 事务锁，防止并发留下孤立归属。该锁适合管理端低频写入；后续若写入量增大，需以保持同一不变量为前提改为归属人级别锁。
- 查询支持有界分页、名称/编号字面前缀与排序白名单，追加 ID 稳定排序。范围筛选先于分页；关联归属人名称只针对当前页。
- 页面包含查询、分页、新增/编辑/归属转移/删除与状态；角色编辑页面提供指定角色选择及可读名称，不能只展示内部 ID。

验收：Owner/Operator/Viewer，all/self/roles 交叉允许与拒绝、范围即时变更、权限与范围聚合、越权授权/分配、角色引用删除、用户与客户归属竞争、分页/排序、唯一编号/软删除、版本冲突、查询基线和实际页面流程。
