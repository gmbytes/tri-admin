# API Token 与开放应用

本设计落实 V3 Task 8，沿用已授权的新 Rust/MongoDB/API 方向。以下期限、额度和分层是本阶段的工程裁定，实施与验证在同一计划中继续，不增加旧系统协议适配或客户/客户端管理业务。

当前已接入管理员 Token、应用/用户管理、独立开放认证、本人资料、应用服务用户业务、共享预算和应用调用日志管理查询，以及相应 Vue 管理页面。Task 8 已通过计划中 D 的完整回归和实际服务验收；整体重构继续实施后续开发工具、tok 和部署阶段。

## 身份与凭据

| 身份 | 用途和凭据 | 权限与失效 |
| --- | --- | --- |
| 管理员交互会话 | 现有管理 JWT/轮换刷新令牌 | 继续使用现有最新角色/数据范围规则 |
| 管理员 API Token | 管理用户自己签发的高熵不透明凭据；只在签发成功响应展示一次 | 固定操作 Scope 与所属用户最新权限相交，数据范围跟随所属用户当前策略；过期、撤销或禁用用户立即拒绝新请求 |
| 开放应用 | 独立应用 ID 与一次性应用密钥，服务间交换 15 分钟应用访问令牌 | 仅开放 API Scope；独立应用身份，无管理员身份或角色；应用密钥轮换使旧应用访问会话失效 |
| 应用用户 | 所属应用内独立的用户名/Argon2id 密码、15 分钟访问令牌和最长 7 天轮换刷新会话 | 应用、用户及会话均需有效；Scope 为登录授予集合与当前用户/应用允许集合的交集；复用刷新令牌撤销对应会话 |

管理 Token 不签发管理员交互会话，也不能代替应用或应用用户凭据。开放令牌使用独立的 `TRI_OPEN_JWT_SIGNING_KEY`、固定独立 audience 和明确 principal kind，不能被管理 API 的 AuthContext 接受。未配置独立密钥时开放认证明确不可用，不回退到管理员签名密钥。

开放认证当前将应用服务与用户分成独立 audience，访问 JWT 始终重新核对数据库中的活动会话、应用状态/Scope、服务密钥版本或用户认证代际。应用服务会话最多 128 项、每用户 32 项活动记录；认证尝试使用独立命名的 IP/账号限流，业务请求使用共享应用预算。注销是只撤销自身会话的凭据操作，不受业务额度耗尽阻止。

不透明秘密由系统随机数生成 32 字节，使用无填充 base64url，公开部分含类型版本和 ObjectId；持久化只留 SHA-256 摘要，固定长度恒时比较。密码继续采用现有 Argon2id，不将低熵密码按 Token 摘要处理。令牌、刷新令牌、应用密钥及密码不进入日志、URL、WebStorage 或列表 DTO。

## 管理员 API Token

`/api/v1/api-tokens` 提供自己 Token 的创建、分页、详情和撤销，其他 Owner 也不能读取别人的 Token。操作要求 `apiTokens.read/write`，签发和撤销仅允许交互会话；Token 自身不能再签发 Token。每人最多 32 个未过期且未撤销 Token。默认期限 30 天、最长 365 天，无永不过期选项。

Scope 为现有权限目录中的明确操作码，不接受 `*` 或未实现操作；签发时不得超过签发者权限。每次使用重新读取活动用户、最新角色权限和数据范围，再与固定 Scope 相交；不能依赖令牌中的旧权限。当前 AuthContext 的 `session_id` 改为明确的 `AdminCredential::Session` / `ApiToken`，不以伪造会话 ID 接入 Token。管理员账号的创建、修改、删除、密码重置和本人改密只接受交互会话，即使 Token 声明对应 Scope 也不能执行，避免通过新账号的密码取得不受原 Token 来源/期限/额度限制的管理会话。用户重置密码/禁用/删除时同步撤销对应 API Token。

签发请求带规范 UUID requestId，指纹绑定名称、Scope、期限、IP 和额度。同键同参只建立一个 Token；首次成功响应含秘密，重放或按请求查询只返回公开元数据和 `secret:null`。网络响应丢失后先查询，秘密不能找回；明确撤销原 Token 后再以新 requestId 签发。授权配置不可原地扩张，变更权限或有效期用撤销并重新签发，名称不作为身份。

已接受的持久导出等异步业务继续按其原有操作者/不可变配置/当前资源权限规则执行；撤销 Token 阻止后续调用，不伪装成取消已经接受的服务器任务。

## 开放应用与应用用户

管理 API 使用 `/api/v1/applications` 和 `/api/v1/applications/{id}/users`，权限为 `applications.read/write`、`applicationUsers.read/write` 和 `applicationLogs.read`。应用配置是共享管理资源；应用用户资料需要应用读取和用户读取权限，不能仅靠应用列表权限取得资料。

应用 code 固定且全局不复用，ObjectId 为认证与数据绑定身份；名称可修改，编辑、启停、密钥轮换和软删除采用版本检查与事务审计。管理端应用/用户写入要求交互会话；开放应用服务的用户操作在下一阶段使用独立开放身份，不构造假管理员。

应用允许的 Scope 显式配置。读取类 Scope（profile/users.read）须具备 applicationUsers.read，写入类须具备 applicationUsers.write；应用创建、密钥轮换、Scope 与策略修改、启用均核对对应授权。只有应用配置写权限时可编辑名称或停用，不能因此取得更高权限的服务密钥。用户管理读取需要 applications.read + applicationUsers.read，写入同时要求 applicationUsers.write。

创建按原管理员/UUID 去重并只首次返回密钥。轮换使用独立 UUID 和原版本，回执固定记录完成时的应用版本/凭据版本；重放只返回当前应用元数据、原回执和空秘密，配置软删除后也不重新执行。回执为有界字段的轻量记录持久保留，不设置会阻止未来安全轮换的生命周期次数上限。

应用用户用户名在应用内规范化唯一，允许不同应用使用相同用户名；所有查询、编辑和会话条件都包含 applicationId。软删除后同名新用户取得新 ID，旧会话不会转投新身份。用户密码只存 Argon2id，不为创建去重另存快速密码指纹；创建响应丢失后查询用户名/版本，不能自动重置密码。用户写入和父应用策略变更共用父记录栅栏，但不因子用户编辑改变公开的应用版本。

密码重置、禁用和删除撤销对应应用用户的会话；应用停用/删除撤销该应用全部会话，重新启用不复活旧会话；应用密钥轮换只撤销应用服务会话。管理端用户凭据操作维持版本检查、密码和审计同事务。实际开放 JWT/刷新拒绝在开放认证阶段验收，当前管理阶段不以会话记录状态冒充完整认证证明。

开放 API 使用 `/open/v1`：

- `POST /auth/application`：应用 ID/密钥换取应用身份访问会话；不发刷新令牌，过期后重新证明应用凭据。
- `POST /auth/login`：应用 ID、应用用户账号/密码及所需 Scope，返回应用用户访问/轮换刷新令牌；不需要把应用服务密钥嵌入玩家客户端。
- `POST /auth/refresh`、`POST /auth/logout`：仅接受对应开放会话凭据，不能操作管理员会话；应用访问令牌注销用自己的访问会话身份。
- `GET/PATCH /me`：仅应用用户身份，读取/编辑自身安全资料，分别要求 `open.profile.read/write`；编辑仅允许 displayName 与版本，不接受密码、身份或 Scope 字段。
- `GET/POST /users`、`GET/PATCH/DELETE /users/{id}` 与 `POST /users/{id}/password`：仅应用身份，要求 `open.users.read/write`，始终限于自身应用；应用用户即使持有同名 Scope 也不能成为应用服务身份。

初始开放 Scope 目录只登记上述四项。用户会话只授予 profile Scope；应用服务会话可按应用允许集合请求更小 Scope。创建/调整用户时的授予不得超过操作者及应用允许集合。游戏 Scope 在后续真实接口实现时登记，不先放行空壳能力。

应用用户刷新只保留原会话的授权上限，再与当前应用/用户 Scope 相交，不通过刷新扩大旧会话。应用访问令牌也绑定可撤销访问会话；禁用、注销或密钥轮换后的旧会话不会因 JWT 尚未过期而继续可用。

管理端和开放端用户写入复用同一事务核心，但授权为显式分支：管理员保留真实交互会话、当前角色和管理员审计；应用服务重新核对真实应用会话与有效 Scope，并使用应用主体审计，actorId 为空。创建、授予 Scope、重新启用与密码重置均不能超出该令牌有效的 profile 授权上限；同一条业务不会借用应用创建者的管理员权限。

## IP、预算和调用日志

每个管理员 Token 和开放应用配置每分钟限额、UTC 日配额及最多 32 条 IPv4/IPv6 CIDR。默认每分钟 600 次、每日 100000 次；可设每分钟 1–10000、每日 1–10000000，不提供无限额。空 CIDR 列表表示不限制来源；配置来源限制时，缺失真实 socket IP 必须拒绝。只使用服务 socket 的 ConnectInfo，不信任任意 X-Forwarded-For；生产反向代理的可信来源方案单独由部署配置验收。

应用的预算由该应用全部服务/用户会话共享，管理员 Token 独立计数。通过来源检查的有效凭据请求，包括 Scope 拒绝结果，按一次请求计数；来源被拒绝仍记调用日志但不消耗目标预算，错误秘密不能消耗被猜测 Token/应用的预算，认证失败使用单独的 IP 限制。IPv4 映射的 socket 地址按原 IPv4 规范化后核对 CIDR。MongoDB 原子预算记录先于业务执行提交，跨实例不能并发突破额度；返回 429 并提供 Retry-After。重复提取同一请求身份不重复扣量。

预算授权与调用开始日志在同一事务登记，日志无法持久化时不执行业务。完成后记录安全结果，若结果日志更新失败，保留未确认开始记录，不伪造成功。日志仅含请求 ID、已登记 operationId/route、身份/应用 ID、来源 IP、状态、错误码、耗时和时间；不记请求/响应正文、查询原值、凭据、个人密码或任意路径。分页按应用/身份/结果/时间过滤，保留 30 天并有有界清理。

管理端应用调用查询要求 applications.read + applicationLogs.read，先按 applicationId 和保留期限过滤，再以同一快照计数/分页；身份、用户 ID、状态和时间均为受控筛选。应用软删除后，具备权限者仍可按原 ID 查询保留期内历史，供故障与安全审计使用；其他应用的记录不会混入。

## 验收

真实副本集验证一次性签发、同键冲突/并发唯一性、摘要、过期/撤销、所属用户即时失效、Scope 交集和角色范围变化。真实 HTTP 证明三类身份不能混用、不同应用同名用户互不读取、刷新复用撤销、密钥轮换、IP/CIDR 拒绝和伪造转发头无效、并发预算及安全调用日志。

管理界面提供 Token、应用、应用用户和调用日志；一次性秘密只在当前签发结果内存展示，丢失响应可查询但不能还原。只读账号没有创建/修改/轮换控件。现有管理员登录/刷新、文件/导出、版本及日志必须继续通过适当回归；不以接口骨架或纯内存替身作为 Task 8 完成证据。
